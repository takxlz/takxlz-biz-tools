# agents

Claude Code のサブエージェント定義（`*.md`）置き場。ここは実行するツールではなく、
Claude Code に読み込ませる資産のディレクトリ。

## 収録エージェント

| ファイル                                 | 用途                                                       |
| ---------------------------------------- | ---------------------------------------------------------- |
| [loop-verifier.md](loop-verifier.md)     | 自律ループの1周ごとの独立検証。continue / done / escalate を判定 |

## インストール

Claude Code は `~/.claude/agents/`（全プロジェクト共通）と `<repo>/.claude/agents/`（プロジェクト限定）を読む。
このリポジトリはあくまで保管場所なので、使う側からリンクするか複製する。

```sh
# 全プロジェクトで使う
ln -s "$PWD/agents/loop-verifier.md" ~/.claude/agents/loop-verifier.md

# 特定プロジェクトだけで使う
cp agents/loop-verifier.md /path/to/project/.claude/agents/
```

リンクにしておくとここを直せば全プロジェクトに反映される。複製した場合は追従しない。

## loop-verifier

### 何のためのものか

「ループエンジニアリング」（1回のプロンプトを磨くのではなく、エージェントを回し続ける仕組みの側を設計する
やり方）で一番壊れやすいのは、自律性そのものではなく **検証・停止条件・人間へのエスカレーション**。
`/loop` や cron でエージェントを回すと、実装した本人が自分の成果を検証するため
「直したつもり」で緑判定が出て、ループが空回りしたまま回り続ける。

loop-verifier は、その判定だけを**別コンテキストの第三者**に切り出したもの。
実装の経緯を知らない状態で成果物と実行結果だけを見るので、作業側の思い込みを引き継がない。

### 使い方

ループの各周の最後に呼ぶ。ゴール・完了条件・検証コマンド・直前の失敗を渡すほど精度が上がる。

```
loop-verifier サブエージェントで検証して。
ゴール: tsv-filter に --out を実装する
完了条件:
  1. -o out.tsv 指定時に stdout は空
  2. 未指定時は従来どおり stdout に出る
  3. node --test "*/*.test.js" が緑
  4. README に --out の記述がある
検証コマンド: node --test "*/*.test.js"
反復: 3周目 / 直前の失敗: 条件2が落ちた
```

`/loop` と組み合わせる場合は、ループのプロンプト側に
「1周ごとに loop-verifier で検証し、`done` なら loop を止め、`escalate` なら人間に報告して止める」
と書いておく。判定の「進捗ログ」行を作業ログのファイルに追記していけば、
次の周のエージェントが過去の失敗を読める（ループの外部記憶になる）。

### 非自明な挙動

- **read-only**。`tools` は `Bash, Read, Grep, Glob` で Edit / Write を持たない。
  検証者が修正までやると「自分の直したものを自分で合格にする」構図に戻るため、意図的に分けている。
  テストの緩和や skip も提案止まりにさせている（緑にするだけならいくらでもできてしまうので）。
- **判定は3値**。`continue` / `done` に加えて `escalate` を必ず持たせている。
  合否だけだと、進まないループが `continue` を出し続けて止まらない。
- **`未検証` を合格に寄せない**。確かめられなかった項目は不合格でも合格でもなく未検証として残す。
- **出力は短く固定形式**。毎周呼ぶのでトークンが積み上がる。実行ログの引用は要点のみに制限している。
- モデルは指定していない（呼び出し元を継承）。検証の質を上げたい・コストを抑えたい場合は
  frontmatter に `model:` を足す。
