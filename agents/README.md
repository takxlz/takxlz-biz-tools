# agents

Claude Code のサブエージェント定義（`*.md`）置き場。ここは実行するツールではなく、
Claude Code に読み込ませる資産のディレクトリ。

収録しているのは**ループエンジニアリング**（1回のプロンプトを磨くのではなく、エージェントを
回し続ける仕組みの側を設計するやり方）のためのスイート。ループの局面ごとに1体ずつ、
役割が重ならないように分けている。

## 収録エージェント

| ファイル                             | 局面     | 役割                                                             |
| ------------------------------------ | -------- | ---------------------------------------------------------------- |
| [loop-designer.md](loop-designer.md) | 開始前   | 曖昧なゴールを、検証可能な完了条件・停止条件・記録先まで落とした仕様にする |
| [loop-scout.md](loop-scout.md)       | 各周の頭 | LOOP.md の未達から次の1件を選ぶ。尽きたら「作業なし」で終了させる |
| [loop-verifier.md](loop-verifier.md) | 各周の尻 | 1周を独立検証し `continue` / `done` / `escalate` を判定する       |
| [loop-doctor.md](loop-doctor.md)     | 数周ごと | 周の並びを診て、空回り・骨抜き・膨張を検出し継続可否を勧告する    |

いずれも **read-only**。`tools: Bash, Read, Grep, Glob` で Edit / Write を外し、
Bash 経由の書き換え（リダイレクト・`sed -i`・git の状態変更）は各定義の禁止事項で縛っている
（検証コマンドの実行に Bash が必要なため、ツール面だけでは完全に縛れない）。
実装するのは呼び出し側のメインエージェントで、この4体は「決める・探す・確かめる・診る」だけを担う。

## 使い方の流れ

全体像。実装するのは常にメインエージェントで、4体は判断だけを返す。

```
[開始前]  loop-designer ──→ LOOP.md（契約）── 内容をレビューしてから回す
             │
             ▼
[各周]    loop-scout ──→ 実装（メインエージェント） ──→ loop-verifier ──→ loop-log.md に1行追記
             │  ▲                                           │
             │  └────────────── continue ───────────────────┤
             │                                              ├─ done ──→ 終了
             └─「作業なし」（未達が尽きた）──→ 終了          └─ escalate ─┐
[数周ごと / escalate 時]  loop-doctor ──→ 続行 / 仕様修正 / 停止 / 人間へ ←┘
```

### 1. 設計する（ループ1本につき1回）

対象リポジトリで Claude Code を開き、ゴールを渡す。

```
loop-designer で「<ゴール>」をループ仕様にして。
```

返ってきた Markdown を `LOOP.md` として保存する。**「未確定・要判断」に質問が残っていたら、
答えて反映してから回す**（曖昧なまま回すのが一番の無駄）。チームで使う場合はこの `LOOP.md` を
PR にしてレビューを通すと、完了条件・禁止事項・自律レベルの合意がここで取れる。

### 2. 回す

`/loop` に次の雛形を貼る（間隔・周期は作業に合わせて調整）。

```
/loop 15m LOOP.md の完了条件を1つずつ潰す。
各周: (1) loop-scout で次の1件を決める。「作業なし」なら loop を止める。
      (2) 実装する。大きい変更ならプランを立ててから実装する。
      (3) loop-verifier で検証する。「差し戻し」なら次の周は取り消しから始める。
      (4) 判定の「進捗ログ」行を loop-log.md に追記し、STATE.md を更新する
          （scout の「状態ファイルの整理」も反映する）。
      done なら loop を止め、escalate なら loop-doctor を呼んでから止める。
3周ごとに loop-doctor を呼び、「停止」「人間に引き渡し」なら loop を止めて報告する。
```

### 3. 終了する

ループが終わるのは次のいずれか。**終了はエージェントの故障ではなく設計どおりの動作**。

- `done` … verifier が全完了条件の合格を確認した（リスク中以上なら人間レビュー推奨が付く）
- `作業なし` … scout が「`LOOP.md` の未達が尽きた」と判断した。仕様外の発見は
  scout の出力に提案として残るので、続けたければ人間が `LOOP.md` を改訂して回し直す
- `escalate` / doctor の「停止」「人間に引き渡し」 … 人間の判断待ち。停止理由の欄に
  「何を判断してほしいか」が書かれているので、それに答えて仕様を直してから再開する

### 単発でも使える

ループを組まなくても、各エージェントは独立して呼べる。

```
# 大きめの実装をさせた直後に、第三者の目で裏取りする
loop-verifier で検証して。ゴール: ○○。完了条件: 1)… 2)…

# 次に何をやるべきか迷ったとき（LOOP.md が無ければリポジトリを走査する）
loop-scout でこのリポジトリの直すべき点を探して。

# 長く回した後、続ける価値があるか迷ったとき
loop-doctor で直近のコミットと loop-log.md を診断して。
```

### 外部記憶（ログ）の約束

ループが前の周を覚えていないと、同じ失敗を延々と繰り返す。エージェント側ではなく
**ファイル**に持たせる。役割の違う3つを混ぜないこと。

| ファイル      | 役割                                                     | 書き換え             |
| ------------- | -------------------------------------------------------- | -------------------- |
| `LOOP.md`     | 契約（ゴール・非ゴール・完了条件・停止条件・自律レベル・禁止事項） | ループ中は書き換えない |
| `STATE.md`    | 現在の状態（節は「着手中 / 待ち・保留 / 未解決の疑問 / 見たが無視した」に固定） | 毎周更新し、片付いたら消す |
| `loop-log.md` | 履歴（`<日時> \| <周> \| <判定> \| <一手> \| <結果>`）    | 追記のみ             |

`LOOP.md` は loop-designer が書式ごと出す。`loop-log.md` の行は loop-verifier 出力末尾の
「進捗ログ」をそのまま足す。loop-scout は `STATE.md` / `loop-log.md` を読んで掘り返しを避け、
loop-doctor は3つと git 履歴を突き合わせて診断する。**記録を書かないと後半2体が機能しない。**

`STATE.md` を剪定せずに膨らませると、状態が腐って幽霊項目が残る。scout の出力に
「状態ファイルの整理」欄があるのはそのため。

## インストール

Claude Code は `~/.claude/agents/`（全プロジェクト共通）と `<repo>/.claude/agents/`（プロジェクト限定）
を読む。このリポジトリはあくまで保管場所なので、使う側からリンクするか複製する。

```sh
# 全プロジェクトで使う
for f in "$PWD"/agents/loop-*.md; do ln -s "$f" ~/.claude/agents/; done

# 特定プロジェクトだけで使う
cp agents/loop-*.md /path/to/project/.claude/agents/
```

リンクにしておくとここを直せば全プロジェクトに反映される。複製した場合は追従しない。

## 設計メモ（非自明な判断）

- **なぜ全部 read-only か** … 検証者や診断役が修正までできると「自分で直して自分で合格にする」構図に
  戻り、独立した目という存在理由が消える。テストの緩和・skip・完了条件の書き換えも、提案までに留めさせている
  （緑にするだけならいくらでもできてしまうため）。
- **なぜ verifier と doctor を分けたか** … 見る単位が違う。verifier は1周の中身、doctor は周の並び。
  1周ずつは正しく見えるのに全体では進んでいない、という失敗は1周の中からは見えない。
  同じエージェントに両方やらせると、直近の1周に引きずられて傾向を見落とす。
- **なぜ scout が「作業なし」を返せるようにしたか** … ループの停止条件は「完了」だけではない。
  作業の発見役が候補をひねり出す性質を持つと、ループは永遠に終わらない。
- **なぜ scout の作業ソースを LOOP.md の未達に限定したか** … チームのリポジトリでは作業の
  ソースはチケットと計画であり、エージェントがコードベースを漁って勝手に作業を起案するのは
  善意でもスコープ外の変更になる。未達が尽きたらループは終了し、仕様外の発見は提案として
  残すだけ（`LOOP.md` を改訂して対象に含めるかは人間が決める）。自由走査は仕様が無い
  単発利用のときだけ。
- **なぜ designer を回す前に置くか** … 空回りの原因はたいてい実行時ではなく設計時に仕込まれている
  （完了条件が検証不能・停止条件が無い・1周が大きすぎる）。検証手段が無いリポジトリでは、
  「まず検証手段を作る」ことを最初のループにするよう提案させている。
- **判定は3値** … `continue` / `done` に加えて `escalate`。合否2値だと、進まないループが
  `continue` を出し続けて止まらない。
- **`未検証` を合格に寄せない** … 確かめられなかった項目は不合格でも合格でもなく未検証として残す。
- **出力は短く固定形式** … 毎周呼ぶのでトークンが積み上がる。実行ログの引用は要点のみに制限し、
  次の周にそのまま渡せる形にしてある。
- **モデルは未指定**（呼び出し元を継承）。verifier / doctor の精度を上げたい、scout を安く回したい
  といった調整は各 frontmatter に `model:` を足す。

## 参考にした実装との対照

提唱者側の公開物と突き合わせて、取り込んだ点と意図的に外した点。

**取り込んだ点**（[loop-engineering](https://github.com/cobusgreyling/loop-engineering) の
`loop-verifier` / `minimal-fix` / `loop-triage` / `loop-intake` / `loop-constraints` と
[Loop Design Checklist](https://github.com/cobusgreyling/loop-engineering/blob/main/docs/loop-design-checklist.md)・
[Anti-Patterns](https://github.com/cobusgreyling/loop-engineering/blob/main/docs/anti-patterns.md) より）

- 検証者の既定の立場を「不合格」にする（合格の理由ではなく落とす理由を探す）
- 変更範囲・禁止パス（`.env`・鍵・認証・課金）・抜け道（テスト削除/skip）の確認
- リスク中以上なら、テストが緑でも人間レビューを推奨する
- 判定とは別に「変更の受理 / 差し戻し」を返す（不足なのか、入れてはいけないものが入ったのか）
- 自律レベル L1 報告のみ → L2 補助 → L3 無人 の段階導入と昇格条件
- 同じ対象で3回失敗したらエスカレーション（試行回数の上限）
- 非ゴールの明示、外から止める手段（キルスイッチ）、契約 / 状態 / 履歴の3ファイル分離

**意図的に外した点**

- **実装役（maker）のサブエージェント化** … 参照実装は `minimal-fix` を別エージェントにしている。
  ここでは実装を呼び出し側のメインエージェントに残した（人間が見ている前提なら、
  文脈が続く分そちらが速く安い）。チェックリストも実装者と検証者の分離を
  「エージェント・モデル・指示のいずれかで分ければよい」としており、read-only の検証者を
  独立させた時点で条件は満たす。**無人（L3）で回すなら maker を別に立て、worktree で
  隔離するべき**——そのときはここに1体足す。
- **予算監視のエージェント化** … 参照実装は skill + CLI（`loop-cost`）で見ている。
  消化量の集計は決定論的な処理で足りるので、上限は `LOOP.md` に置き、doctor の所見に
  「消化」欄として持たせるに留めた。
- **対話的な要件詰め** … 参照実装の `loop-intake` は「一度に1問ずつ人間に聞く」方式だが、
  サブエージェントは人間と直接対話できない（呼び出し元に返るだけ）。loop-designer は
  代わりに「未確定・要判断」として質問リストを返す形にしてある。
